## 1. 语言、构建与辅助环境

正式求解器从 A0 开始使用 C++ 核心和 CUDA 后端。优先标准库及成熟数值库，先正确运行、诊断和 benchmark，后做专门性能优化；必要的正确性 CUDA 实现不等于提前启动性能优化。

采用 CMake 组织目标、依赖与构建，配合 Ninja 和 CTest。C++20 是待首个构建验证的工程基线建议；编译器/Toolkit 组合、CUDA 架构、第三方库版本、精度与性能范围还须实测登记。当前没有 CMakeLists.txt 或可执行文件，不能把本文示例称为已经构建通过。

| 文件/工具 | 管理对象 |
|---|---|
| CMakeLists.txt、cmake/ | C++/CUDA 目标、头文件、编译和链接依赖 |
| CMakePresets.json | 可共享的 CPU/CUDA、Debug/Release 配置，不硬编码个人绝对路径 |
| CMakeUserPresets.json | 本机 Toolkit/依赖前缀、个人配置；不进入 Git |
| pyproject.toml、uv.lock、.python-version | 辅助 Python/PyTorch 对照、输入生成和后处理环境 |
| `build/<preset>/` | 构建缓存、目标文件和二进制；不进入 Git |

现有 uv 环境保留，`package=false` 不变，不把求解器改成 Python 包。C++ 程序无需通过 uv 启动；辅助 Python 工具使用自己的 uv 环境。现有 PyTorch 包带 CUDA 13.0 用户态库，公共 Toolkit 为另一套安装；CMake 显式定位所选 Toolkit，不把 Python 包内库目录加入全局链接搜索路径。LibTorch 是可评估的 C++ 数值依赖，不是使用 C++ 的必需条件，也尚未选定。

C++ 标准库不提供完整 FFT/稠密分解。GPU 的 cuFFT/cuBLAS/cuSOLVER 是已有候选；CPU FFT/线性代数、TOML/JSON/NPZ 适配库在相应伪代码和首个构建中逐项确定并固定版本。CMake 不是包锁文件：实际引入的库必须记录精确版本/提交、来源、许可证、下载内容哈希和构建选项。当前不增加依赖管理器或自动下载依赖。

## 2. 目标代码树

下列是逐模块落地的布局；没有实现的模块不创建空接口或空测试冒充功能。

```text
fomhd/
  CMakeLists.txt
  CMakePresets.json
  cmake/
  include/fomhd/             对外 C++ 接口与数据类型 .hpp
  src/
    core/                   状态、阶段、单位/布局、错误和资源所有权 .cpp
    geometry/               网格、实体、权和边界拓扑 .cpp
    numerics/               兼容算子、Fourier、数值库适配 .cpp
    fluid/                  主离子与电子流体 .cpp
    fields/                 Darwin 与 CT .cpp
    boundary/               壁约束与反力 .cpp
    time/                   阶段组织、A0 推进；以后 A1 调度 .cpp
    diagnostics/            只读约束、收支与误差诊断 .cpp
    io/                     配置、状态、checkpoint、运行清单 .cpp
    cuda/                   CUDA 实现 .cu；内部共享声明按需用 .cuh
  app/                      C++ CLI/运行入口 .cpp
  tests/                    单元、集成、回归测试 .cpp/.cu
  cases/                    小型标准输入、生成配方和验收说明
  tools/                    辅助分析/输入工具，按需要可用 .py
  jobs/                     Slurm 脚本
  docs/
    development.md
    pseudocode/             可直接翻译、随代码分支版本化的实现说明书
  pyproject.toml
  uv.lock
  .python-version
  build/                    忽略的构建产物
  tmp/                      忽略的可再生临时文件
```

物理和时间算法共用同一套核心，不为 A0–A3 复制四套源码。host/device 拥有者、只读视图、分配/释放时机、同步点和工作区复用须显式；CPU 与 CUDA 共用数学合同和状态语义，不要求所有函数都走运行时虚接口。资源管理采用 RAII，借用视图不得越过其拥有对象生命周期。

阶段协调器组织流体源/响应、场解及完整 RHS；数值模块不依赖文件读写。时间推进拥有接受/拒绝和唯一状态提交；diagnostics 返回记录，io 消费记录。物理上的双向耦合通过显式数据对象和调用顺序表达，避免互相调用造成循环依赖。RHS 表示半离散演化导数，包括通量散度、力与其他项，不仅是物理源项。

## 3. 伪代码是实现规格与维护说明书

完整链条为：连续方程 → 离散算法定义 → 实现级伪代码 → C++/CUDA → 独立数值核验。

算法层解释选什么及为什么；伪代码精确说明数据如何经过索引、分支、求解、同步、检查和提交。不得用“处理边界”“求解场”这样的未展开名称掩盖关键实现选择。成熟库调用可以是叶节点，但必须给定输入布局、精度、归一化、工作区、返回码和物理残差要求。

每个模块的伪代码至少包含：

1. 稳定步骤 ID、数学符号到代码字段的映射、引用的公式/决策及版本。
2. 输入/输出、单位、形状、索引范围、交错位置、模式顺序与实复类型。
3. 状态/工作区的所有权、允许修改的对象、host/device 位置及生命周期。
4. 完整循环、分支、边界/空集合/非法状态处理，库调用和同步顺序。
5. 阶段、试算、迭代与接受语义；失败时留下什么，哪些量绝不提交。
6. 后置条件、独立参考测试、负对照和运行诊断的对应关系。

未来正文放在本仓库 `docs/pseudocode/`，与对应实现和测试同一次变更维护；设计库保留数学权威及索引，不另存可独立编辑的同名全文。步骤 ID、源符号和测试名用于映射，避免依赖易变的源码行号。每个维护分支保有自己匹配的伪代码；旧版本以提交/tag 中的文件为准。

伪代码先于对应模块实现，但允许小型、可撤销的探针验证索引、数值库接口和关键假设。探针发现问题先修规格再落正式实现。伪代码不是正确性证明；独立制造解、收敛、守恒和 restart 检查仍必须运行，不把照抄伪代码的测试当独立证据。

当前仅建立本约定；完整 A0 伪代码尚未生产。

## 4. master、维护分支与不可移动标签

默认分支名为 `master`。主要开发从短期 `codex/<task>` 分支开始，通过复核与相应测试后合入 master。master 推进到 A3 时，可以保留能复用的早期运行模式，但精确重现旧版本使用相应发布标签。

每个阶段第一次通过明确范围的 benchmark 后，在同一个提交上建立：

- 不可重指的标签，例如 `a1-v1.0.0`：对应一份精确代码、伪代码和验收记录。
- 可继续前进的维护分支，例如 `release/a1`：维护 A1 的修复与后续改进。

目前没有任何 A0–A3 已通过 benchmark，不预先创建这些标签或维护分支。tag 表示实际验收范围，不等于全物理范围已通过。

例如 A1 增加更真实边界，先从 `release/a1` 建任务分支，更新边界标识、伪代码、输入/重启兼容规则和对应 benchmark，复核后合回，发布新 tag。旧 `a1-v1.0.0` 不变。改变物理边界必须保留原参考条件与适用范围，不能当作不影响结果的小修复。

跨版本通用修复用单独提交选择性回移并重测；不盲目把整个 master 合进旧维护分支。分支增多会增加回移和验证成本，只有实际需要维护的阶段长期保留分支。分析报告固定 tag/commit，不能只写会移动的 `release/a1`。

多人同时用不同版本时采用不同 clone 或 Git worktree、各自的 build 目录；运行中的任务使用固定二进制及匹配库，不在其使用路径上重编译覆盖。版本清单记录源码提交、未提交状态、可执行文件哈希、编译参数和实际动态库版本。

正式 benchmark 使用干净提交。调试允许未提交修改，但须保存相对提交的完整补丁以及实际参与构建的未跟踪源码，或保存完整源码快照，并逐文件校验哈希；仅有 commit 和 dirty 标记不足以重建源码。快照范围明确限定为项目输入，排除环境、凭据和无关数据。

源码远程为用户的 GitHub `ziyu59151/fomhd`，默认 private。设计仓库仍为本地仓库。初始源码基线只含工程说明和原有辅助环境配置，不上传设计历史、文献、运行数据、.venv 或其他用户文件。本次建库不授权之后的任意发布、改为公开、加协作者或更改账号设置。

## 5. 运行目录与数据来源

本机公共运行根（用户个人目录）为 `/home/lxzeng/runs/`，按项目名分组，例如：

```text
~/runs/
  fomhd/
    a0-wave_reference__20261103T120000Z__7c21/
    a1-wave_dt_scan__20261103T121000Z__b8d0/
  gtc/                      使用时再创建
```

先输入项目名，再输入有辨识度的算例前缀，即可 Tab 补全；时间和唯一后缀放后面。程序通过显式输出路径接受此目录，不在源码中硬编码家目录。每次运行拒绝复用非空目录；源码、build、输入副本和结果分开。

每次运行保存 inputs、logs、history/checks、snapshots、checkpoints 和失败现场；run.json 关联实际配置与输入哈希、源码/二进制/设计版本、依赖、设备、精度、随机种子、Slurm 信息及完成状态。原始输入须保留，哈希不能替代数据；大型输入可以引用不可变副本并登记位置。resume 使用新目录并指向原 checkpoint，不覆盖旧运行。

临时 checkpoint 完整写入后原子更名，最后更新 latest 指针；失败候选不能作为 restart。图表和拟合是派生产物，单独记录输入 run ID 和分析代码版本。运行产物不进入源码 Git；重要结果独立备份。日志是运行过程，结构化诊断才是残差/预算/科学判定的依据。

## 6. 最小依赖和调用记录

依赖信息分别放在构建目标/锁定来源、模块接口文档和运行清单中。用 CMake target 声明链接关系；启用 compile_commands.json 供编辑器导航/分析，它记录编译命令，不是完整调用图。源码是实际调用关系的权威；文档只维护关键模块图、阶段时序、数据所有权和步骤 ID 映射，不手抄每个调用。

首个 C++/CUDA 构建前完成依赖/API 对应与往返测试计划：标准库不等于所有数值/I/O 库，不能把 Python API 名称原样留作 C++ 实现。现有 TOML/JSON/CSV/NPZ 是逻辑数据方案，采用经过验证的原生适配；若改容器格式，须先同步设计和 schema，不暗中引入 Python 求解器运行时依赖。

所有版本说明区分：已定义、已实现、已测试、已通过指定科学 benchmark。没有实际求解器与测试时，不用空 CMake 目标或零测试集合宣称构建/核验完成。
